Agent 的"大脑"是 LLM（大语言模型）。不理解它，写出来的 Agent 就总在出一些"玄学"问题。今天把最关键的几个概念过一遍。

## Token：模型计价的单位

模型读写文本的最小单位不是"字"，而是 Token——大致对应半个到一个汉字，或四分之三个英文单词。两件跟 Token 直接相关的事：

1. **计费**：几乎所有商业 API 都按 Token 计费，输入和输出分开计价；
2. **上下文限制**：模型一次能处理的 Token 总量有上限，超出部分要么被截断、要么报错。

所以"把整本书塞给 Agent"是不现实的，长内容需要切片或摘要，这会在后面记忆和 RAG 的文章里展开。

## 上下文窗口与注意力

模型每次推理能"看到"的内容叫上下文（Context）。一个常见的误解是：模型"记住"了历史对话。实际上它什么都没记，只是每次调用时，把全部历史消息重新拼进提示里再计算一次。这就是为什么：

- 对话越长、花费越高、响应越慢；
- 超长历史会稀释模型的注意力，让早期信息"被遗忘"。

Agent 开发者的日常，就是管理好这个上下文：保留重要的、裁剪无用的。

## 三个最常调的参数

| 参数 | 作用 | 对 Agent 的建议 |
| --- | --- | --- |
| temperature | 输出随机性，越高越发散 | 需要稳定执行时调低（0-0.3） |
| max_tokens | 单次输出上限 | 预留够用，避免被截断 |
| 模型版本 | 越新的模型推理越强 | 优先选支持"工具调用"的版本 |

工具调用（Function Calling）是 Agent 的命门，下一篇会单独讲。选模型时务必确认它原生支持该能力。

## System Prompt：Agent 的"人设与规则"

一次 API 调用里，消息通常分三类：`system`（系统设定）、`user`（用户输入）、`assistant`（模型回复）。Agent 的做法是把"你是谁、你要干什么、什么能做、什么不能做、输出什么格式"全部写进 system 消息：

```text
你是博客写作助手。
你的任务：根据用户给的提纲，写一篇中文技术博客。
规则：只能使用用户提供的资料；结构清晰；不编造数据。
输出：Markdown 格式，先给标题，再给正文。
```

系统提示词写得好不好，直接决定 Agent 的表现上限。它值得被当作代码一样认真维护与版本管理。

## 小实验建议

动手永远是理解最快的路径。建议你用任意一家大模型 API（或用本地模型）做两个对比：把 temperature 分别设成 0 和 1 各跑十次同样的指令，观察稳定性的差异；再写一个带 system 规则的助手，看看规则约束是否真的生效。下周我们讲提示词工程，这些实验会很有帮助。
