写提示词和写代码很像：目的都是把"模糊意图"翻译成"机器能稳定执行的东西"。只不过提示词的编译器是模型本身，它宽容、有理解力，但也有自己的脾气。面向 Agent 的提示词，重点不是"让它回答得漂亮"，而是"让它稳定地走对流程"。

## 原则一：给角色，更给目标与边界

只写"你是专家助手"没太大用。有效的角色设定包含三层：

1. 身份：你是谁，具备什么能力；
2. 目标：这次任务要达成什么结果，衡量标准是什么；
3. 边界：哪些不能做、资料不足时怎么办、超出范围怎么反馈。

```text
你是代码评审助手。
目标：对用户提交的代码片段给出问题清单，标注严重程度。
边界：只评审用户贴出的代码，不猜测项目上下文；
资料不足时明确说"缺少 X 信息"，不要编造。
```

## 原则二：结构化输出优先于自由文本

Agent 的下一步逻辑经常要读取模型上一步的输出。如果输出是自由散文，程序解析就很容易出错。更稳的做法是要求 JSON 等结构化格式，最好附上字段说明：

```text
以 JSON 返回评审结果，格式如下：
{
  "summary": "总体评价（一句话）",
  "issues": [
    { "severity": "high|medium|low", "line": 数字, "reason": "问题说明" }
  ]
}
只输出 JSON，不要输出其他文字。
```

如果 API 支持 JSON 输出模式或结构化输出（Structured Outputs），务必打开——它会比"在提示词里要求"可靠得多。

## 原则三：少样本示例胜过千言万语

模型对"抽象规则"的遵循，通常不如对"具体例子"的模仿。给一两个高质量的正例（最好再配一个反例），效果立竿见影：

```text
输入：帮我订明天北京到上海的高铁
输出：{"action": "search_trains", "params": {"date": "明天", "from": "北京", "to": "上海"}}

输入：查一下上海的天气
输出：{"action": "get_weather", "params": {"city": "上海"}}
```

## 一些实践要点

- **让模型说"不"**：明确允许它拒绝不合理请求，能大幅减少幻觉式执行；
- **一次只做一件事**：单个 Agent 的提示词职责越单一越可控，复杂任务交给多个 Agent 分工（六月会讲多智能体）；
- **提示词要版本化**：把提示词当作代码管理，改动前后跑一遍回归，否则你根本不知道是哪句改动影响了表现；
- **警惕"过度承诺"**：不要在提示词里要求模型做它做不到的精确计算或实时查询，那应该交给工具。

## 本课小结

一句话版本：**好的 Agent 提示词 = 清晰的目标 + 严格的边界 + 结构化的输出约定 + 几个好例子**。下周我们进入 Agent 的"手脚"——工具调用，看看模型是怎么真正"动手做事"的。
