单步的 ReAct 适合"查个天气"这种小任务。一旦目标是"写一份行业分析报告"或"把整个项目重构完"，模型就容易顾此失彼——做着做着忘了初衷，或者在一个细节里钻牛角尖。这时就需要**规划**能力：先想清楚做什么、按什么顺序做，再动手。

## 规划的三层结构

| 层次 | 粒度 | 例子 |
| --- | --- | --- |
| 目标层 | 最终要达成的结果 | 产出一份可发布的行业报告 |
| 任务层 | 达成目标需要的子任务 | 调研资料 / 整理框架 / 逐节撰写 / 校对 |
| 执行层 | 每个子任务的具体行动 | 搜索关键词 X 并记录要点 |

规划的本质，就是**把目标层递归地下沉到执行层**，并且记录每步的状态（待做 / 进行中 / 完成），让循环可以随时回答"我现在在哪、下一步做什么"。

## 两种主流实现

### 方式一：显式计划 + 逐步执行（Plan-and-Execute）

先用一次（或几次）LLM 调用生成任务清单，再让执行循环按清单逐项推进，每完成一项就更新状态、必要时动态调整后续任务：

```text
[用户] 写一篇 3000 字的小型创业公司增长策略分析

[Planner 输出]
1. 调研：该公司所处行业与近期动态
2. 框架：确定分析维度（产品/获客/留存/变现）
3. 撰写：按框架逐节起草
4. 校对：检查事实、补数据、润色
（依赖：1→2→3→4，步骤间可能有并行）

[执行器] 我现在执行第 1 步：调研……
```

好处是可控、可中断、可向用户展示进度；代价是计划可能过时，需要"计划-执行-再计划"的循环来修正。

### 方式二：隐式规划（让模型边走边想）

不生成独立清单，而是靠良好的提示词让 ReAct 循环内部自然规划，例如要求模型"每次行动前先回顾整体目标，说明这一步如何服务于目标"。适合任务较简单、步骤<5 的场景，省一次额外调用。

## 规划 Agent 的工程骨架

规划器与执行器分离是常见的成熟结构：

```python
def planner(goal: str) -> list[dict]:
    # 让 LLM 输出任务清单 JSON: [{"id","desc","depends_on"}]
    ...

def executor(task: dict, memory: dict) -> None:
    # 用 ReAct 循环执行单个子任务，结果写回 memory
    ...

def run(goal: str):
    tasks = planner(goal)
    done = set()
    while len(done) < len(tasks):
        ready = [t for t in tasks if t["id"] not in done
                 and all(d in done for d in t["depends_on"])]
        if not ready:  # 有依赖环或任务不可达，终止
            break
        for t in ready:
            executor(t, memory)
            done.add(t["id"])
    return compose_output(memory)   # 汇总各部分结果
```

## 四条实用经验

- **规划输出必须是结构化 JSON**（含依赖关系），否则无法程序化调度；
- **单任务执行也要限步**：规划器拆出的子任务同样可能失控，给执行器独立的步数上限；
- **允许中途改计划**：执行中发现事实与假设不符，应触发"重新规划"，而不是硬着头皮走完；
- **人类可审查**：把计划呈现给用户确认后再执行，是"重要任务"场景最值得的投资。

## 小结

规划让 Agent 从"反应式"进化为"目标式"。到这里，三月份的"四大要素"（大脑、工具、记忆、规划）就全部过了一遍。五月份进入工程实践：先用 RAG 给 Agent 喂知识，再对比主流框架，最后用 LangGraph 把整套流程编排成可维护的代码。
