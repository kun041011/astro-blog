前面四个月，我们大部分时候在"手写"：自己维护消息、自己写循环。手写让你懂原理，但真实项目追求的是效率与可维护性。今天横向对比主流框架，回答两个问题：**要不要用框架？用哪个？**

## 先回答"要不要用"

我的判断标准很朴素：

- 任务 < 5 步、逻辑固定 → **手写**：依赖少、可控、好调试，别为小需求引框架；
- 流程复杂、分支多、要状态持久化 → **上框架**：自己维护循环的状态机和重试会很快失控；
- 团队协作、要长期演进 → **上框架**：框架提供的抽象（图、状态、追踪）是团队沟通的语言。

## 主流框架速览

| 框架 | 核心抽象 | 擅长场景 | 学习曲线 |
| --- | --- | --- | --- |
| LangChain | 链（Chain） | 快速拼装 LLM 调用与工具 | 低 |
| LangGraph | 图（Graph）/ 状态机 | 复杂可控的 Agent 流程 | 中 |
| AutoGen | 多 Agent 对话 | 多智能体协作、代码执行 | 中 |
| LlamaIndex | 数据索引与检索 | 知识密集型 RAG 应用 | 低 |
| 原生 SDK + 手写 | 无 | 简单任务 / 深度定制 | 看水平 |

## 各自怎么选

### LangChain：老兵，生态最全

组件化程度高，文档、教程、集成（几百个第三方工具）都是最多的。代价是抽象层多，出问题时"黑盒感"强。适合：快速验证想法、需要大量现成集成。

### LangGraph：给流程装上了方向盘

把 Agent 流程建模成**有向图 + 状态机**：节点是步骤，边是条件跳转，状态在节点间流转。它解决了 LangChain 时代"流程写死在代码里、难调试难分支"的痛点，支持人类审批节点、循环、超时。**是目前构建生产级单/多 Agent 流程的主流选择**，下篇专门实战。

### AutoGen：让多个 Agent 开讨论会

主打多 Agent 对话与代码执行。多个角色（如"程序员""评审员"）互相发消息推进任务。适合探索性、开放式问题。代价是对话式协作的收敛性和可预测性弱一些，需要约束。

### LlamaIndex：数据人的 RAG 首选

如果你 80% 的需求是"问答我的文档"，LlamaIndex 在数据接入、索引、查询引擎上体验最好，Agent 只是它的一层外壳。文档类 Agent 可以优先看它。

## 我的选型建议（2026 年经验）

1. **简单问答/文档**：LlamaIndex 或直接手写 RAG；
2. **单 Agent 多工具、流程明确**：LangGraph；
3. **流程需要人审、超时、重试、状态恢复**：LangGraph（这些是它的主场）；
4. **多角色协作研究**：AutoGen / LangGraph 的子图模式；
5. **纯学习**：什么都别装，继续手写两个月再说。

## 警惕"框架锁定"

框架的抽象层是双刃剑：跟着框架走，迭代快；框架变动或不再维护，迁移成本高。缓解办法：**核心逻辑写在独立的纯函数里**（工具、检索、校验），框架只做"编排外壳"。这样将来换框架，业务代码几乎不用动。

## 小结

框架不解决模型能力问题，它解决的是**工程问题**：状态、分支、重试、观测、协作。下周我们选 LangGraph 实战一把，把这套"图编排"的思想落到能跑的代码上。
