前五个月我们一直在打磨"一个 Agent"。六月第一课讨论：**什么时候需要多个 Agent？它们怎么协作？**

## 先泼盆冷水：默认用单 Agent

多 Agent 不是勋章。每多一个 Agent，就多一层消息传递、多一份不一致的可能、多一批要观测的日志。业界有个共识方向：**尽量把复杂任务压缩进一个 Agent**——给它更好的提示词、更多的工具、更大的上下文，往往比拆分多个更稳。

那什么时候才拆？三个信号：

1. **角色需要的提示词/工具差异巨大**（比如"代码编写"与"安全审查"几乎无交集）；
2. **需要不同模型**（廉价模型做分类、强模型做推理）；
3. **天然存在并行子任务**（同时调研多个主题）。

## 两种主流协作模式

### 主从模式（Supervisor / Orchestrator）

一个"主管"Agent 负责任务拆解、调度与汇总，其余"工人"Agent 各自只做一件事：

```text
用户目标
   │
主管 Agent ── 决定派给谁、合并结果、必要时重派
   ├─→ 工人A（调研）
   ├─→ 工人B（数据分析）
   └─→ 工人C（撰写）

主管知道"谁擅长什么"，工人不关心全局。
```

优点：结构清晰、可控、好加人审；缺点：主管是单点，主管能力不足时全盘受限。

### 议事模式（Debate / Conversation）

多个 Agent 围绕同一问题互相质疑、补充，最后收敛出结论：

```text
研究员：给出初步结论
评审员：指出漏洞、要求补证据
研究员：回应并修订
……直到达成一致或达到轮数上限
```

优点：适合开放式、需要多视角校验的问题；缺点：可能跑偏、绕圈、成本高，收敛性依赖强约束（轮数上限、终止条件）。

LangGraph 里，主从模式就是"主管节点 + 条件边分发"，议事模式就是"带终止条件的循环子图"——上个月的图抽象在这完全复用。

## 角色设计：像带团队一样

多 Agent 的成败在"角色说明书"：

- **边界要硬**：工人 Agent 只接受本领域任务，越界必须上报主管，而不是硬做；
- **交付格式要统一**：所有 Agent 的输出约定为结构化格式，主管才好合并；
- **上下文要隔离**：别把全量对话广播给所有 Agent——每个 Agent 只应看到与自己相关的部分，否则 Token 爆炸且互相干扰。

## 一个反面教训（真实复盘）

我曾把"写周报"拆成三个 Agent（收集、分析、撰写），结果收集和撰写都各自调用了一遍分析工具，周报里出现两处不一致的数据。改成**单 Agent + 明确工具顺序**后反而稳定了。这个例子说明：**为拆而拆只会引入重复劳动与冲突**，拆分必须对应真实的能力/权限差异。

## 观测是协作的前提

多个 Agent 之间的消息流如果不记录，出了问题连"是谁传错了话"都查不到。所以多 Agent 上线前，先保证能回答：谁在何时调用了谁、传了什么、结果是什么。这正好接上下一篇的主题——可观测性。

## 小结

多智能体 = 用工程手段组织多个受限的专家，而不是放任它们自由聊天。优先单 Agent，必须拆分时选对模式、写清边界、统一格式、做好观测。
