普通程序"要么对要么错"，Agent 是概率系统：同样的输入，今天成功明天抽风。没有观测手段就上线 Agent，等于闭眼开车。今天讲清楚三层观测：**日志、追踪（Trace）、评测（Evaluation）**。

## 第一层：结构化日志

至少要记录每一次 LLM 调用的五要素：时间、模型、system/user 消息、输出、Token 用量。手写 Agent 时最便宜的方案是自己在循环里打日志：

```python
def call_llm(messages, **kw):
    t0 = time.time()
    resp = raw_call(messages, **kw)
    logger.info({
        "event": "llm_call",
        "model": kw.get("model"),
        "input_tokens": resp.usage.prompt_tokens,
        "output_tokens": resp.usage.completion_tokens,
        "latency_ms": int((time.time() - t0) * 1000),
        "messages": messages,          # 完整上下文，排障必需
        "output": resp.content,
    })
    return resp
```

关键点：**上下文必须完整落盘**。缺了上下文，出问题时你无法重放模型的"所见"。

## 第二层：追踪（Tracing）

单条日志看不出"整条链路"：Agent 可能调了工具、查了记忆、又问了模型三次。追踪把一次任务的所有调用串成一棵树（Trace），每个节点是一次 LLM 调用或工具执行，含父调用关系、耗时、输入输出。成熟的工具链包括 LangSmith、Langfuse、Phoenix 等；就算不用工具，也要在自己代码里给每次任务生成一个 `trace_id`，贯穿所有日志。

有了 Trace，两个高频问题立刻可答：

- 这轮回答为什么错？→ 看工具返回了什么、模型在哪个节点开始跑偏；
- 为什么这么慢/贵？→ 看哪个节点 Token 多、哪次调用重试了。

## 第三层：评测（Evaluation）

日志只能回答"发生了什么"，评测回答"做得怎么样"。三层递进：

### 1. 规则评测（最便宜）
程序化检查输出：是否含禁用词、JSON 是否合法、是否引用了指定字段、步骤数是否超限。能自动跑的规则全部自动跑。

### 2. 答案对比
准备"问题-标准答案"集，对比模型输出与参考答案的相似度/包含度。适合有确定答案的检索问答。

### 3. LLM-as-Judge（最灵活）
让一个"裁判模型"按评分标准给输出打分。给裁判写清楚维度（准确性、完整性、格式、是否有幻觉），并附上标准答案与检索到的资料：

```text
你是评测员。请按 1-5 分评价助手回答。
评分维度：是否准确、是否忠于所给资料（不得编造）、是否完整。
资料：{context}
标准答案：{reference}
助手回答：{answer}
输出 JSON：{"accuracy": 分数, "faithfulness": 分数, "completeness": 分数, "reason": "简短理由"}
```

注意裁判自身的偏差：让它先看资料再看回答、要求给出理由、同一批样本多次评测取均值，都能降低抖动。

## 评测集怎么来

- **先攒 30-50 条真实/仿真任务**作为种子集，覆盖正常、边界、拒绝类；
- 每次改动（换模型、改提示词、改索引参数）后全量回归；
- 关注三类核心指标：任务成功率、平均步数与 Token 成本、严重错误率。

## 上线后的持续观测

评测是"考试"，生产还缺"监控"：

- 失败率与重试率：工具连续失败要告警；
- 成本与延迟：Token 用量的环比突变往往意味着循环失控；
- 用户反馈闭环：加"点赞/点踩"，把差评样本定期回流进评测集。

## 小结

日志让你能"复盘"，追踪让你能"定位"，评测让你能"量化"，监控让你能"预警"。四者缺一，Agent 项目就只能靠玄学迭代。下一篇讲如何给 Agent 装"刹车"——把关键决策交给人类。
