Agent 由 LLM、外部 API、网络三部分组成，每一环都可能失败：模型抽风返回乱码、工具超时、服务限流。生产环境的功课，就是把这些"随机失败"用工程手段兜住，让系统的可靠性可以量化、可以承诺，而不是听天由命。

## 失败模式清单

先盘点 Agent 最常遇见的失败，再对症下药：

| 失败 | 表现 | 典型原因 |
| --- | --- | --- |
| 输出格式错 | JSON 解析失败 | 模型不听话 / 上下文太长 |
| 调用超时 | 工具一直不返回 | 外部服务慢 |
| 限流 | 429 / 退避 | 调用太频繁 |
| 循环 | 反复做同一件事 | 目标不清 / 观察没传回 |
| 幻觉 | 编造工具结果 | 上下文缺事实 |
| 中断 | 进程重启、任务丢失 | 长任务无状态保存 |

## 五个基础但关键的工程件

### 1. 超时（Timeout）

每一次外部调用都必须有超时。LLM 调用、工具调用、整体任务各设一档，逐层收窄：工具 30 秒、单轮模型 2 分钟、整任务 N 分钟。没有超时的 Agent 会被一个卡死的 API 拖住全部用户。

### 2. 重试（Retry）与指数退避

瞬时失败（网络抖动、限流）值得重试，但要有退避和抖动：第一次等 1 秒、第二次 2 秒、第三次 4 秒，并加随机抖动防止惊群。**只对"可重试"的错误重试**：超时、5xx、限流可以；4xx 参数错误、业务校验失败重试也没用。

### 3. 幂等（Idempotency）

重试的前提是"重复执行没有副作用"。给每个任务/请求生成唯一 ID，工具执行前检查是否已处理过；对外部系统（发消息、下单）尤其重要——否则一次重试可能让用户收到两封邮件。实现上：调用方带 `request_id`，服务方记录已处理的 ID 并直接返回原结果。

### 4. 限步与熔断

四月的 ReAct 我们就有 `max_steps`，生产里还要升级成两级：**单任务限步 + 全局熔断**。当某个 Agent 或某个工具在窗口期内失败率飙升（如连续 10 次失败），熔断器打开，后续请求快速失败并告警，而不是继续撞墙。

### 5. 状态持久化与恢复

长任务（几分钟到几小时）必须能"断点续跑"。把每一步的状态（当前任务、已完成步骤、中间结果）写入存储；进程重启后从中断处继续，而不是从头再来。LangGraph 的 Checkpointer（五月提过）就是为此设计的。

## 格式错误的"自我修复"

模型输出非法 JSON 是最高频的坑，标准做法是**纠错循环**：解析失败就把错误信息（如 "Expecting property name enclosed in double quotes"）连同原文塞回对话，让模型修正后重试，最多两三次。配合"结构化输出"能力（如果模型支持）可从源头规避。

## 降级与优雅失败

系统不可能永远成功，要设计"失败时的最低可用形态"：

- **降级**：检索服务挂了 → 退回模型直接回答并明示"未检索资料"；付费模型限流 → 切备用模型；
- **优雅失败**：宁可明确说"我现在做不了，请稍后再试"，也不要让 Agent 编一个成功结果。这属于安全底线，六月人审那篇强调过，这里再重复一次：**不要用幻觉掩盖故障**。

## 把可靠性变成数字

最后，把上面所有努力落实为可观测的指标（接六月可观测性那套）：

- 任务成功率、单步重试率、熔断触发次数；
- 平均延迟与 P95/P99；
- 单任务 Token 成本与超限率。

有了这些数字，"这周比上周稳/差了多少"就有答案，改动效果也能量化。

## 小结

可靠性没有银弹，是一组朴素工程件的组合：**超时保底、重试处理瞬时失败、幂等让重试安全、限步防失控、持久化防丢失、降级保底线**。下周我们反着问一个问题：什么时候干脆别用 Agent？
