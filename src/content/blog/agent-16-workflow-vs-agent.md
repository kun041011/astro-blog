学了半年 Agent，最容易犯的职业病是"看什么都是 Agent"。今天这课是反方向的修炼：**识别哪些问题根本不需要 Agent**，以及如何在工作流与 Agent 之间做出理性选择。

## Agent 的隐藏成本

Agent 的灵活是有代价的，每一轮"自主决策"都意味着：

- **Token 消耗**：思考、工具结果回传、历史累积，通常比固定流程贵数倍；
- **延迟**：多轮调用叠加，响应时间翻几番；
- **不确定性**：同样的输入，结果可能不同——需要评测与护栏兜底（六月那套）；
- **排障成本**：自由路径越多，复现和定位越难。

当任务"其实有确定答案"时，这些成本全部是浪费。

## 工作流 vs Agent：一条判断线

一个常用的判断框架（来自业界实践）：**路径是否预先可知**。

- **工作流（Workflow）**：预先编好固定的调用顺序，适合路径已知、稳定的任务；
- **Agent**：由模型动态决定调用路径，适合路径未知、需临场判断的任务。

举例：

| 任务 | 该用哪个 | 理由 |
| --- | --- | --- |
| 客服工单自动分类 | 工作流 | 分类规则确定，无需求变化 |
| 财报数字抽取入库 | 工作流 | 步骤固定，LLM 只做一步翻译 |
| 写一篇调研文章 | Agent | 资料取舍、行文结构需要临场决策 |
| 定时汇总并群发周报 | 工作流 | 模板固定，改动只发生在数据源 |

用一句话记住：**能用固定步骤表达的，就别交给自由发挥**。

## 混合才是常态

现实系统中两者常常嵌套：**外层是工作流（固定的骨架），内层节点里用 Agent（处理不确定的环节）**。例如"周报系统"：收集数据、渲染模板、发送是固定的编排；"把散乱素材整理成周报条目"这一步可以交给 Agent。骨架保证可控，Agent 在局部提供智能。

五月 LangGraph 那篇里的图本身就是为这种混合而生的：把 Agent 当图上的一个普通节点，其余节点是普通函数。

## 成本账怎么算

选型前建议做一个粗算，以"每次任务"为单位：

```text
成本 ≈ 输入 Token × 输入单价 + 输出 Token × 输出单价
      × 平均轮数 × 失败重试放大系数
```

例如：单轮 2 万输入 Token + 5 千输出，约几毛钱级别；但一个 8 轮、带 2 次重试的 Agent 任务可能放大到几十倍。**把"每单成本"和"每单收入/价值"放一起看**，很多"炫技型 Agent"会立刻显得不划算。

降本三板斧：

1. **能省则省**：用便宜的小模型处理简单环节（分类、改写），贵模型只做关键推理——多智能体那篇讲过的"不同模型分工"；
2. **上下文瘦身**：每轮只带必要信息（四月记忆篇的裁剪/摘要）；
3. **能固定就固定**：把高频稳定环节从"让模型想"改成"代码直接做"。

## 判断清单：上线前问自己五问

1. 这个任务的步骤是不是其实已经固定？
2. 换成规则/工作流，能不能覆盖 80% 的输入？
3. 用户真的需要"动态规划"吗，还是只要一个稳定结果？
4. 多花的 Token 和延迟，换来的是不是用户感知得到的质量提升？
5. 出错时，自主路径会不会让"找原因"变得很难？

如果前三问里有任何一个"是"，先做工作流；后两问答不上来，先别上 Agent。

## 小结

Agent 的定位应该是"**工具箱里最后才拿的那把**"：先用规则、工作流、确定性代码解决大部分问题，把 Agent 留给真正需要判断与应变的部分。懂得不用 Agent，和懂得用 Agent，同样重要。下一篇，我们进入八月实战收官：把六个月的知识整合成一个完整的"博客写作 Agent"。
