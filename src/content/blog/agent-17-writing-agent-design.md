八月是收官月。我们做一个真实的综合项目：**一个能辅助撰写本博客的写作 Agent**——输入一个主题，它负责检索资料、拟大纲、分节起草、按风格润色，最后由人确认后生成符合本站 frontmatter 规范的 Markdown 文章。目标不是"一步生成全文"，而是"可控地辅助人完成全流程"。

## 第一步：需求与边界（先回答十六课的五个问题）

对照七月那篇"什么时候不该用 Agent"：

1. 步骤固定吗？→ 大体固定（检索→大纲→起草→润色），但每步的内容取舍需临场判断 → **混合架构**：固定骨架 + Agent 节点；
2. 规则能覆盖 80% 吗？→ 不能，写作质量依赖模型 → 值得上 Agent；
3. 用户要的是稳定结果吗？→ 要质量也要可控 → **保留人工确认点**；
4. 成本可接受吗？→ 每篇文章一次任务，量小，成本可控；
5. 出错好排查吗？→ 靠 trace 记录每步，可回放。

结论：采用"工作流骨架 + Agent 起草/润色 + 人在关键节点把关"。

## 第二步：流程设计（画图先行）

用五月 LangGraph 的图思维，把整个流程画成节点与条件边：

```text
用户主题
   │
[规划节点] 检索资料(RAG) → 生成大纲 → 人工确认大纲
   │ 确认通过
[起草节点] 逐节调用模型撰写正文（每节约 300-500 字）
   │
[润色节点] 统一风格、补标题层级、检查 Markdown 语法
   │
[生成产物] 组装 frontmatter + 正文 → 输出 .md 草稿
   │
[人工终审] 确认后写入 src/content/blog/ 目录（此步必须人点）
```

三个刻意设计：

- **大纲要人工确认**：写作方向错了，后面全白写，此处值得一次人工介入（六月人审篇）；
- **发布是硬闸门**：写好的草稿只落到"待发布"位置，真正移入博客目录、提交推送由人来完成——这是不可逆的高影响动作；
- **每节独立起草**：把长文切成小节逐段写，避免一次生成超长内容导致质量滑坡（也方便中途修正）。

## 第三步：工具与知识设计

这个 Agent 需要的工具集：

| 工具 | 作用 | 对应所学 |
| --- | --- | --- |
| search_notes | 检索本站已有文章，避免重复、保持风格一致 | 四月记忆 / 五月 RAG |
| search_web | 补充外部事实资料 | 工具调用（三月） |
| draft_section | 起草单个小节 | ReAct 节点（四月） |
| polish_text | 按站内风格润色 | 提示词工程（三月） |

风格保持一致的小技巧：把本博客 2-3 篇旧文章切成示例块，作为起草时的 few-shot 参考（三月提示词篇的"少样本"），比在提示词里描述"要通俗、带表格、结尾有小结"有效得多。

## 第四步：明确质量定义

上线前先定"什么叫写好"，否则迭代没依据（六月可观测篇）：

- 大纲通过率：人工确认时一次通过的比例；
- 事实错误数：草稿中与检索资料不符的表述；
- 返工率：润色后仍需人工大改的比例；
- 单篇成本与耗时。
