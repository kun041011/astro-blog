从三月初识 Agent 到八月完成写作助手实战，这条学习线走完了。最后一篇不写新知识，做一次诚实的复盘：我们学了什么、哪些弯路值得标记、接下来往哪走。

## 六个月的知识地图

按时间线回看，这其实是一条刻意设计的路径：

| 阶段 | 月份 | 主题 | 掌握的核心 |
| --- | --- | --- | --- |
| 打地基 | 3 月 | 概念 / LLM / 提示词 / 工具 | 四大要素，模型只是大脑 |
| 核心机制 | 4 月 | ReAct / 记忆 / 规划 | Agent 循环与三个支撑件 |
| 工程实践 | 5 月 | RAG / 框架 / LangGraph | 从手写走向可维护 |
| 系统思维 | 6 月 | 多智能体 / 可观测 / 人审 | 从单个走向系统 |
| 生产落地 | 7 月 | MCP / 可靠性 / 成本 | 从 demo 走向产品 |
| 综合收官 | 8 月 | 写作助手实战 | 把前面全串起来 |

如果只能留三条最值得记住的，我会选：

1. **Agent = 循环 + 记忆 + 工具 + 边界**，而不是"调一下模型 API"；
2. **可控优先于智能**：固定流程、人审闸门、评测回归，缺一不可；
3. **成本与可靠性是产品属性**：能不用 Agent 就不用，用了就要能观测、可兜底。

## 踩过的坑（实战向清单）

- **幻觉式执行**：模型假装调用工具。对策：结果必须来自工具回传，system 明确禁止臆造；
- **工具越多越乱**：一次挂十几个工具，选择准确率明显下降。对策：分层按需挂载；
- **上下文越长越笨**：早期信息被稀释。对策：裁剪、摘要、按需检索；
- **没有评测就"优化"**：凭感觉改提示词，越改越玄。对策：先建评测集，改动必回归；
- **为拆而拆多 Agent**：两个 Agent 重复调同一工具，数据不一致。对策：默认单 Agent，拆必须有真实分工；
- **发布无闸门**：让 Agent 直接对外动作。对策：不可逆动作一律人工确认。

## 一个重要的认知更新

六个月的实践里我最深的体会：**Agent 的瓶颈往往不在模型，而在系统设计**。同一个模型，提示词、工具、记忆、护栏设计得好，表现可以天差地别。这也是为什么这条路值得从"地基"一步步走上来——跳过基础直接套框架，遇到问题只会"换模型"，而不会诊断系统。

## 下一步往哪走

给继续学习的人几个方向（也是我自己接下来的计划）：

1. **深耕一个垂直场景**：把写作助手这类项目打磨到"天天用、离不开"，比再做十个 demo 有价值；
2. **研究评测与自动优化**：用评测数据反哺提示词/工具设计，做"Agent 的 Agent"；
3. **关注模型能力演进**：上下文变长、推理变强后，哪些设计可以简化（比如更少依赖外部记忆），保持跟进但别追热点；
4. **补工程短板**：向量库调优、流式体验、多租户权限——这些"不性感"的能力决定产品上限。

## 结语

如果这篇系列能帮到一个人少走弯路，就值了。最后送你一句半年里最实用的话：**把 Agent 当作一个需要被设计、被约束、被观测的系统，而不是一个可以许愿的盒子**。感谢阅读，江湖再见。
